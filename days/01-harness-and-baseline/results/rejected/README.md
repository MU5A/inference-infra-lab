# Rejected results: do not cite

These files came from measurement attempts that were disturbed by something else on the machine.
They are kept as evidence of what interference looks like, and so that nothing is quietly dropped.
**None of their numbers may be used in a claim.** The only Day 1 results that may be cited are in
`../baseline_llama_server.json`.

| File | What was wrong |
|---|---|
| `warm_cache.json` | Taken with the pre-flight clean at the start, but decode varied by up to 6.9% (one sample at 127.9 against 150 elsewhere), so something interfered mid-run. The size of the effect, a prompt cache cutting time to first token from tens or hundreds of milliseconds to about 10, is far larger than that noise. The exact numbers are not citable. |
| `llama_bench.json`, `llama_bench.environment.json` | Decode at 60.5 tokens/s with a standard deviation of 50.2 (samples 148.9, 36.1, 48.4, 43.8, 25.4) while a video player used the GPU. The pre-flight at the time looked only at CPU load and could not see it. An earlier, better llama-bench run was overwritten before it was saved to a committed file, so no raw data exists for it. |
| `harness_overhead.json`, `harness_overhead_profile.txt` | Three runs began with a clean pre-flight, but the load average was 6.4 by the end. Tails were large (p95 3 to 11 ms) and two earlier discarded runs had smaller ones, so load average did not predict the tails. The measurement has to be repeated under conditions that are verified throughout, not only at the start. |
| `cache_comparison_attempt2_unstable.json` | Pre-flight clean at the start, then the warm long-prompt run was unstable (time to first token variation 13%, above the 10% limit) and decode fell from about 111 to 101 tokens/s, with the short prompt's speed-up only 3.4x against a predicted 5x. The short prompt's floor was about 7 ms of server overhead rather than prefill time. The sampler of that time looked at CPU only, and the GPU peaked at 85% near the end, so this file carries no GPU record and the cause is a diagnosis, not something this file proves. |
| `llama_bench_attempt2_unstable.json` | Prompt processing was steady (3227.4 tokens/s, variation 0.1%), but the decode samples were 166.0, 165.5, 163.7, 29.8 and 50.6 tokens/s (variation 59.7%). Two samples collapsed while the CPU neighbours were quiet and the GPU peaked at 85% near the end of the run. As above, no GPU record was written into the file. |
| `cache_comparison_attempt3_slow.json` | The third attempt. Cold phase fine (decode 155 to 161 tokens/s), then the warm phase slowed down: short 157, medium 103 and long 86 tokens/s, with the medium and long warm runs failing the variation limits (time to first token 11.9% and 6.8%, decode 12.0% and 10.8%; the long one failed on decode). The `gpu_contended` and `peak_gpu_percent` fields in this file are meaningless: the sampler counted the benchmark's own GPU use, and it has since been removed. |
| `llama_bench_attempt3_slow.json` | Run straight after the cache phases. Steady but slow: prompt processing 779.5 tokens/s (variation 0.3%) and decode 55.7 (variation 0.4%), against 3,227 (attempt 2, whose decode samples ranged from 29.8 to 166.0) and a decode baseline of 152.5. Repeats cannot see a machine that is slow the whole time, which is why a reference probe was added. Same note on the GPU fields. |
| `cooldown_probe.txt`, `cooldown_probe.sh` | A diagnostic, not a measurement: the script waited 240, 300 and 420 seconds and then ran a short decode-only llama-bench each time. Decode was back at 166 tokens/s after the first wait and stayed there. Right after attempt 3, two quick probes of the same kind had given 46 and 55 tokens/s, and memory bandwidth measured 84.5 GB/s, so memory was not the problem and the Metal backend was in use. The slowdown went away with rest. The machine is a fanless MacBook Air (Mac15,12), so heat is the likely cause, but no temperature or clock was read, so it is not proven. |
